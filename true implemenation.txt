# 2. WORKSTREAM 1 — Data & persistence foundation

## Objective

Make it nearly impossible for the system to:

* lose user data
* create inconsistent data
* calculate from stale state
* corrupt data during updates
* restore malformed backups
* behave like a new user after deployment

IndexedDB is an appropriate local-first foundation, but schema changes must happen through versioned upgrade transactions, and transactional writes should be treated as the atomic boundary. ([MDN Web Docs][1])

---

## Current issues

### 1. Monthly date bug

The current code contains:

```js
/^d{4}-d{2}-d{2}$/
```

instead of:

```js
/^\d{4}-\d{2}-\d{2}$/
```

This can prevent the expected monthly lifecycle from triggering.

### 2. Date handling is inconsistent

Some places use:

```js
new Date().toISOString().split('T')[0]
```

while other code uses:

```js
localDateStr()
```

That can produce UTC/local-day boundary errors.

### 3. Browser AI secret is session-only

Current browser fallback:

```js
let memoryFallback = new Map();
```

So:

```text
browser refresh
   ↓
API key gone
```

while IndexedDB data remains.

### 4. Migration testing isn't deep enough

The database is already at v11 with a large number of stores.

That means future migrations are a major risk.

---

## Technical approach

Create one persistence architecture:

```text
UI
 ↓
Domain service
 ↓
Repository
 ↓
IndexedDB
```

No direct database writes from random components.

---

## Implementation

### 1. Central date service

Create:

```text
src/helpers/dateHelpers.js
```

Canonical APIs:

```js
localDateStr()
localDateTime()
parseLocalDate()
addDays()
subtractDays()
daysBetween()
startOfDay()
endOfDay()
isToday()
```

Rule:

```text
Human day → local timezone
Database timestamp → ISO
```

---

### 2. Installation metadata

Create an `appMeta` store:

```json
{
  "id": "installation",
  "installationId": "...",
  "firstInstallDate": "...",
  "schemaVersion": 11,
  "lastMigrationVersion": 11,
  "lastSuccessfulBoot": "...",
  "onboardingVersion": 5
}
```

---

Instead of implicit migration logic becoming scattered:


Every migration should have:

```text

```

```json
  "schemaVersion": 1,

  "createdAt": "...",
  "stores": {}
```

# 33. Techniques to use throughout

These are the engineering patterns I would deliberately standardize.

### State machines

Use for:

```text
onboarding
sync
migration
action execution
calibration
```

### Domain services

Use for:

```text
goal progression
score calculation
today recommendations
evidence processing
```

### Repository pattern

Keep all IndexedDB access behind repositories.

### Zod contracts

Use at boundaries:

```text
AI
backup
domain events
actions
integrations
```

### Event-driven updates

Use domain events to notify:

```text
score
insights
UI
Jarvis
audit
```

### Transaction boundaries

Critical multi-record mutations should use one transaction where possible; IndexedDB provides atomic transactions for this style of operation. ([MDN Web Docs][2])

### Optimistic UI only when reversible

Don't optimistically update critical state unless rollback is guaranteed.

### Idempotency

Your Jarvis action executor already has an execution-key approach.

Expand this across:

```text
sync
actions
scheduled analysis
migration
imports
```

### Provenance

Every important insight should know:

```text
what data
when
source
confidence
```

### Feature flags

Use for risky new intelligence:

```text
adaptiveToday
calibrationV2
jarvisPlansV2
proactiveInsightsV2
```

# 34. What could block the whole program?

There are five major risks.

## 1. Trying to redesign everything simultaneously

Avoid:

```text
UI redesign
+
scoring rewrite
+
Jarvis rewrite
+
DB migration
```

in one branch.

---

## 2. Changing the database too aggressively

IndexedDB version upgrades are special version-change transactions; migration must be carefully tested and old connections need to be handled correctly. ([MDN Web Docs][3])

---

## 3. AI overreach

Never let:

```text
LLM output
```

become:

```text
truth
```

Always:

```text
LLM
 ↓
schema
 ↓
validation
 ↓
domain rules
 ↓
approval
```

---

## 4. Too much personalization too soon

The system must be able to say:

> "Not enough evidence yet."

---

## 5. Deployment/update instability

Your Vite app has dynamic imports. A stale client can request a chunk that no longer exists after a deployment, so update recovery needs an explicit strategy such as graceful reload handling or asset/version management. Vite documents this exact version-skew failure mode. ([vitejs][4])
